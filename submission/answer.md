## Thesis: the risk is at ingest, not in the broker

Every answer to this brief is going to open by picking a broker. That is the
least interesting decision on the table. Kinesis, MSK and self-managed Kafka
all move bytes, all publish pricing, all carry an SLA. Pick any of the three
and you will be fine.

What will actually hurt you is in the ingest path, and the sample data proves
it. Three events in that file break a constraint the brief calls
non-negotiable, and not one of them looks broken at a glance:

- **`evt-0009`** arrives from an older SDK generation using 4 different field
  names [Observed]: `timestamp`, `page_path`, `ref`, type `pageview`. The brief forbids
  requiring customers to upgrade, so that shape is permanent. Reject it and a
  paying customer silently loses data.
- **`evt-0007`** carries a raw email address and phone number while `user_id`
  is still null; **`evt-0022`** resolves that visitor to `u-7304` fifteen
  events later. **`evt-0017`** is a GDPR deletion demand for `u-1077`, whose
  own history includes **`evt-0006`**, written while they were anonymous.
  Deleting rows keyed on `user_id` leaves pre-identification history behind,
  and an incomplete deletion is a regulatory failure rather than a bug.
- **`evt-0011`** has no `tenant_id`. Across 500 tenants, attributing it by
  inference is not a data-quality issue: it is one customer seeing another
  customer's visitors.

So ingest is the component I built, ran, and measured. All three claims above
come from `results/findings.json`, regenerated by `pipeline/run.py`.

## 1. Architecture and technology choices

```mermaid
flowchart LR
  SDK["JavaScript SDK<br/>unchanged"] --> GW["API Gateway<br/>+ Lambda"]
  GW --> KDS[("Kinesis<br/>Data Streams")]
  KDS --> FL["<b>Managed Flink</b><br/>normalize - classify<br/>keyed state"]
  FL -. malformed .-> DLQ[("Dead-letter<br/>S3")]
  FL ==> DDB[("DynamoDB<br/>visitor state")] ==> PERS["Personalization<br/>API"]
  FL ==> PG[("Postgres<br/>rollups")] ==> DASH["Real-time<br/>dashboard"]
  FL ==> S3[("S3 lake<br/>Parquet")] ==> ATH["Athena to<br/>warehouse export"]
```

**Figure 1.** SDK to dashboard. The dead-letter branch is drawn deliberately: a
malformed record must never stop the consumer.

### Why each component, and what was rejected

| Component | Chosen | Rejected | Deciding reason |
|---|---|---|---|
| Ingest | Kinesis Data Streams | MSK, self-managed Kafka | Modeled infrastructure is 3.6% of the ceiling [Estimated], so engineer-hours are scarcer than dollars. MSK is cheaper per byte and costs broker operations two engineers do not have. |
| Processing | Managed Flink | Lambda, ECS consumers | Four of the thirteen checks the detector performs cannot be answered from a single event [Observed]. Those need checkpointed keyed state, which a stateless consumer cannot provide at any price. |
| Visitor state | DynamoDB | Redis-only, Postgres | Single-digit-millisecond point lookups on the personalization path, per-tenant partition keys, no capacity planning. |
| Dashboard serving | Postgres rollups | ClickHouse, OpenSearch | The team already runs PostgreSQL. Aggregation happens upstream, so it stores summaries rather than raw events. Reversible - see the tripwire in section 3. |
| Event lake | S3 + Athena | Redshift | The brief requires export to Snowflake and BigQuery; Parquet on S3 is the neutral format both read. |
| Hot cache | ElastiCache Redis | - | Already in their stack. Segment membership, not raw events. |

Per-component cost lines and the unit prices behind them are in
`results/cost_model.json`, generated by `pipeline/cost.py` [Benchmarked].

**The stateless/stateful split is the load-bearing choice.** Normalization and
per-event classification are pure functions of one event, so they scale
horizontally and any worker can process any record. Duplicate detection, burst
detection, identity stitching and deletion scope are not: they depend on what
that specific worker has already seen. That boundary, not the broker, decides
whether the system needs Flink-class state or something simpler. The detector
makes it concrete: 9 checks on one side, 4 on the other [Observed].

### Event structure and identity

One canonical envelope - `event_id`, `tenant_id`, `anonymous_id`, `user_id`,
`type`, `ts`, `received_at`, `properties` - with legacy field names mapped at
the edge from a lookup table rather than in code, so registering the next SDK
generation is a config change rather than a deploy. Every transformation is
recorded, so the pipeline can always answer *what did you change about this
event?*

`ts` is the browser's clock and `received_at` is ours. Both are kept and
neither is used to "correct" the other. Where an old SDK sent no `received_at`,
the field stays null with a note attached. Synthesizing it would make the event
look complete while destroying the only evidence for ingest latency and clock
skew.

**Identity resolves backwards.** A visitor browses anonymously, signs in, and
their earlier events become theirs retroactively. The detector reports four
such stitches in 25 lines [Observed], including `anon-3d0` to `u-7304`, which
retroactively attaches the personal data in `evt-0007` to a named person.
Deletion therefore runs against the anonymous-to-user graph in durable storage,
never against the in-memory window, which is bounded and so returns a lower
bound rather than the truth.

## 2. Scale, reliability and migration

### Sizing, and the number that changes the answer

50M events/day [Observed] is 579 events/second average and 5,787 at the
stated 10x spike [Estimated]. At the 229-byte mean event size measured across
the fixture [Observed], that peak is 1.33 MB/s.

A Kinesis shard provides 1 MB/s **or** 1,000 records/second [Benchmarked],
from the AWS Kinesis Data Streams pricing page. So the peak needs 1.3 shards by bandwidth and 5.8 by
record count [Estimated]. **Record count binds.** A shard saturates its record
limit while using 23% of its bandwidth, and anyone sizing this on throughput
under-provisions by roughly 4x - which is one entirely plausible mechanism
behind "crashes during traffic spikes." Provisioned at 8 shards with 30%
headroom [Assumed].

That result only exists because the event size was measured rather than
guessed. It is the single cheapest measurement in this whole design, and the
full derivation is in `results/cost_model.json` under `sizing`.

### Zero loss, and what degrades first

Delivery is at-least-once, so the pipeline deduplicates on `(tenant_id,
event_id)` rather than `event_id` alone - the SDK does not coordinate IDs
across customers, and collapsing them would delete one tenant's event on
another tenant's collision. `evt-0002` appears twice in 25 lines [Observed],
7.4 seconds apart, which is a retry.

Unparseable records go to a dead-letter sink with their original bytes intact,
never to the floor. `evt-0020` is one missing brace; the obvious consumer dies
on it and never reads the four events after it [Observed]. Scale that to a
crash-looping consumer while the broker keeps accepting writes and you have a
mechanism that produces exactly the kind of loss the brief describes.

Under overload the system sheds load in a stated order, and **ingest never
sheds**: rollup granularity coarsens first, then personalization falls back to
the last cached segment, then lake writes batch larger. The broker is the
buffer, and buffered data is late rather than lost.

Both behaviors are implemented and exercised in `pipeline/normalize.py` and
`pipeline/state.py`; the resulting findings are in `results/findings.json`.

### Migration: per-tenant, with an automatic trigger

The SDK cannot change and 500+ customers cannot break [Observed], so
nothing about the cutover is visible to them.

1. **Fork at the edge.** API Gateway writes to both the existing pipeline and
   Kinesis. The old system stays authoritative. No customer-visible change.
2. **Parallel run.** Both pipelines process everything. "Accuracy verified"
   means, per tenant-hour: event counts agree within 0.1% [Assumed], and an
   `event_id` join leaves no unmatched rows on either side.
3. **Shadow dashboards** for internal review only.
4. **Per-tenant cutover**, smallest tenants first.

**The rollback trigger is automatic and does not need a human.** If any
tenant-hour diverges by more than 0.5% for two consecutive hours [Assumed], or
dashboard p95 exceeds 5 seconds, that tenant reverts to the old pipeline and
pages the on-call. Rollback is per-tenant, so a bad cutover costs one customer
an hour, not all of them. The comparison logic is the same code as
`pipeline/rules.py`, run against both streams.

Two accuracy signals run continuously afterwards [Assumed]. The first is the
client-side counter in `evt-0019`: the gap between what the browser claims and
what the server recorded is a free, continuous measurement of pipeline loss.
The second is new instrumentation - a monotonic sequence number per session,
emitted by the SDK - because gaps in a server-assigned `event_id` cannot detect
loss at all. See section 5.

## 3. Trade-offs and risks

**Optimizing for** correctness you can audit and a system two engineers can
operate. **Sacrificing** peak cost efficiency and, in the MVP, query
flexibility.

Modeled infrastructure is $1,809/month, or 3.6% of the stated ceiling
[Estimated], from [Benchmarked] AWS unit prices, and the
conclusion survives every assumption being wrong by 28x. So the $50K ceiling is
not the binding constraint on this design - two engineers and a three-month
window are. That inverts the usual build-versus-buy call: self-managed Kafka is
cheaper per byte and spends the resource that is actually scarce.

**The MVP explicitly excludes** a columnar serving tier, ML-based
segmentation, per-tenant retention policies, real-time backfill, and
cross-tenant benchmarking. Those are the 6-month system.

**The serving tier is a reversible decision with a computed reversal
condition.** Dashboards are served from pre-aggregated rollups in PostgreSQL,
which this team already runs. At the modeled shape that table holds 100M hot
rows against an assumed comfort ceiling of 250M - 40% utilization, 2.5x
headroom [Estimated]. Three conditions trigger a migration review: hot rollup
rows past the ceiling (leading), dashboard query p95 above 1 second over 7 days
(trailing), or rollup write lag above 30 seconds. This is an option held, not a
migration scheduled. It may never fire.

**With more time I would measure the per-tenant distribution first.** The brief
gives 50M/day as a fleet-wide total [Observed]. 500 tenants averaging 100k/day
is a very different system from 20 tenants at 2M and 480 at 8k [Assumed], and
which one it is changes the serving tier. That is the first thing I would
instrument. Every figure in this section derives from `pipeline/cost.py`; the
tripwire block is in `results/cost_model.json`.

## 5. Three things I would not act on at face value

All three are reproducible against `results/findings.json` via
`pipeline/run.py`.

**1. The number the browser made up.** The brief asks for a "viewed pricing 3x"
segment. `evt-0019` supplies exactly that: `count_today: 3`. The server's own
record for that same visitor, `anon-9f2`, shows **one** pricing page view
[Observed]. A counter computed in a browser cannot be audited, cannot be
recomputed, and is trivially forged. The trap is not spotting bad data - it is
that the brief asks for the feature the bad data would break. Segments are
recomputed server-side from raw events. The claim is stored anyway, in a
separate namespace, because the divergence is a free loss measurement.

**2. The bot cluster.** `evt-0012` through `evt-0015` are four page views in
51 milliseconds from one visitor, all referred by a host containing "scanner"
[Observed]. I flag and quarantine them; I do not delete them. A referrer is
attacker-controlled and plenty of legitimate hosts contain that substring. If
the heuristic is wrong and I deleted, real customer data is gone with no
recovery. If it is wrong and I only labeled, the cost is one column in a table.

**3. The brief's own loss figure.** The brief states ~3% event loss at peak.
This fixture cannot confirm or refute that, and I will not pretend otherwise.
`event_id` runs `evt-0001` to `evt-0024` with no gaps [Observed] - but a
curated 25-event sample would show no gaps whether or not the system leaks, and
we do not even know whether `event_id` is assigned client-side or on receipt.
If the server assigns it, loss is invisible by construction. **What would
settle it:** a monotonic per-session sequence number emitted by the SDK and
reconciled server-side. That is why it is in the week-one scope rather than a
"we would monitor this" sentence.

# Operating artifact

A runnable ingest-validation pipeline in pure Python 3, standard library only.
No dependencies, no Docker, no network. It is the prototype of the component
argued above to be the riskiest, and it doubles as the ingest stage of the
design rather than being a separate demo.

Four modules, split along how stream processors actually execute work:
`normalize.py` (stateless map), `rules.py` (stateless classify), `state.py`
(keyed aggregate over a window), `run.py` (job graph and sinks). Everything in
the first two is a pure function of one event and lifts into production
unchanged; everything that could not satisfy that contract was pushed into
`state.py` rather than smuggled in.

Every number in this document regenerates from these three commands:

```
python -m pipeline.run     fixtures/event_sample.jsonl
python -m pipeline.latency fixtures/event_sample.jsonl
python -m pipeline.cost
```

Outputs land in `results/` and are committed, so the findings are readable
without running anything: `findings.txt`, `findings.json`, `dead_letter.jsonl`,
`latency.txt`, `cost_model.txt`.

# What breaks it

**The sample is 25 events** [Observed]. It cannot establish any rate - not an
error rate, not a loss rate, not a distribution. Every conclusion drawn from it
is about mechanism, not magnitude.

**Every threshold is assumed.** Clock-skew tolerances, the dedupe window, the
burst threshold, the Postgres row ceiling. If real clock skew across the SDK
fleet is distributed differently than guessed, the ladder mislabels events.
These are starting policy, not tuned values.

**The bot heuristic has false positives** by construction. A referrer is
attacker-controlled and a legitimate company could be called anything. This is
why the pipeline labels rather than deletes.

**Deletion scope from the artifact is a lower bound, not the truth.** Keyed
state is bounded, so the in-memory graph knows only what it has recently seen.
Real deletion must run against durable storage.

**Two cost lines are unpriced** - a managed OLAP tier and Aurora - because AWS
did not render their rate tables when checked. With 96% of the ceiling unused
[Estimated] they are unlikely to change the conclusion, but that is a
prediction, not a calculation.

**The per-tenant distribution is unknown**, and it decides the serving tier. If
the fleet is 20 large tenants rather than 500 even ones [Assumed],
the Postgres rollup table is wrong from day one and the tripwire fires
immediately rather than never.

**The latency harness is a simulation.** It has no network, no cluster, no
queue. It isolates and measures the mechanism - that batch-window size
dominates end-to-end latency - and proves nothing about any broker. Method and
exclusions are stated in `pipeline/latency.py`.

# What stays human

Everything below is either irreversible or legally binding. The detector was
deliberately built to label rather than act, precisely so these stay decisions.

**Deleting suspected bot traffic.** Automated flagging, human deletion. If the
heuristic is wrong and the events are gone, there is no recovery; if it is
wrong and they are only labeled, the cost is one column in a table. Asymmetric
risk means the automation stops at the flag.

**The scope of a GDPR deletion.** The pipeline can compute which anonymous
history belongs to an identified user. It should not execute the deletion
unreviewed, because both errors are unacceptable in different directions:
deleting too little is a regulatory failure, deleting too much destroys another
person's data.

**Overriding a rollback.** The rollback itself is automatic and needs no human
- that is the point. But the decision to push a tenant forward again after one
fires is a judgment about whether the underlying cause is understood.

**Attributing a null-tenant event.** `evt-0011` has no tenant [Observed].
Guessing which of 500+ customers it belongs to is a data breach if wrong, so
the pipeline quarantines and a human resolves it against the source
integration.

**Declaring accuracy verified at cutover.** The parallel-run comparison
produces a number. Deciding that the number is good enough to move a paying
customer onto a new pipeline is not a threshold check; it is accountability,
and it needs a name attached to it.

**Tuning any threshold in this system.** Every one is [Assumed]. Changing them
changes what the pipeline considers real, and that should never be an
autoscaling decision.
